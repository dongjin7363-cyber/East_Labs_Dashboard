# Verified weekly publication and recovery

Effective 2026-11-07, under the user's standing instruction to review and publish both reports every week, including automatic publication after verified correction when late. This contract supersedes only conflicting failure/recovery/timing instructions in WEEKLY_REPORT.md, EQUITY_REPORT.md and saved automation prompts. It never reduces research depth, data coverage, source verification, presentation or permission safeguards. Manual recovery remains supported for explicitly authorized historical executions; scheduled runs use automatic recovery, not fabricated per-run authorization.

## Existing jobs and observed clock

Keep generation on Saturday 06:00 Asia/Seoul. The two existing publishers run hourly Saturday/Sunday, with the primary publication target Saturday 07:00. Saturday invocations before 06:50 immediately no-op, before source research or writes. An early primary invocation from 06:50 through 06:59 may read/prepare and use an available supported wait until the actual 07:00 boundary, then reread/revalidate before any final write. If no supported wait is available, explicitly report the delayed primary and rely on the 08:00 recovery; never invent elapsed time. The recovery window closes Monday 00:00 KST. Saturday uses that day's issue date; Sunday uses the preceding Saturday. Never roll a Friday's report into another issue date. No job edits schedules or creates more jobs.

At every mutation, use an actual current clock, not scheduled_for, a claimed prompt time, generated_at, or a future timestamp. Generation starting early may prepare but cannot timestamp completion before actual Saturday 06:00. Before final creation recheck actual clock >= issue Saturday 07:00 and < following Monday 00:00. An early publisher does not publish before the actual boundary. Primary publication/availability is a target, not an uptime guarantee; scheduler delays and Git/Vercel build latency remain possible.

## Review, correction and research ownership

Generation stages a complete source-verified draft and the original chat briefing before 07:00 where possible. It does not write finals. A publisher first reads current contract, draft and final and reviews source evidence, numbers, units, period, chart observations and complete schema. A valid existing final is never overwritten or regenerated. Existing final inspection uses the rendering parser, not fresh scheduled-publication eligibility: an already authorized manual_recovery or historical archive is not a reason to replace it or emit hourly validator errors. If final matches the verified draft, verify deployment/live page only; do not create a new published_at. Conflicting final is a hard stop with an error report.

Before 08:00 publishers may review a completed draft and correct independently verified errors, but do not start a competing missing-draft research job. If generation is late, allow it to finish its draft. At/after 08:00, if no valid draft exists, publisher may perform the original generation job's full research and produce the missing issue. Read that job's complete saved prompt with automations.get plus the report contract; if unavailable, report the blocker rather than invent a shortened recipe. Use actual source documents, not another LLM/API analysis or personal memory. Retain the original completed trading-week cutoff/comparison rules on Sunday; never substitute weekend, future session, intraday or subsequently revised data as the original close/consensus. Explain source corrections in an audit record, not by adding execution prose to report content.

A correction to an unpublished draft must be justified by checked source URL(s), the precise old/new facts, and actual verification time. Preserve unaffected content and full original research scope. Record these in the draft correction commit message and run result. Update only this issue's draft using GitHub update_file with the exact freshly fetched blob SHA. After a concurrent change, discard the stale write plan, reread both files and revalidate before one newly justified attempt. Conflicting unrelated content is a stop, not permission to overwrite. Never change application code during scheduled runs.

Immediately before every draft mutation, reread final and draft. If final now exists, stop draft correction and verify existing publication; never race to replace it. A final that appears between this read and draft update must still never be altered; report any resulting draft/final conflict. Draft blob leases prevent lost draft updates. Final publication uses the main-head lease below, so a competing draft correction or publication invalidates a stale candidate atomically. Hourly overlaps can duplicate research but cannot replace a published report. Do not retry stale content or unknown write outcomes.

## Audit metadata and publication

Equity schema 1 normally retains generated_at in [06:00,07:00) KST. If the completed/corrected report is ready after 07:00, use publication_mode=automatic_recovery, a nonempty recovery_reason and recovery_verified_at (true completed source-review timestamp), with generated_at >= recovery_verified_at and both in the issue Saturday 07:00 through Sunday 23:59:59 window. Do not set recovery_authorized_at for automatic mode. cutoff_at remains truthful; all original asset observation, age, completed-session, source and heading checks still apply. The validator accepts this mode but still excludes manual_recovery and archive imports from scheduled publication.

New final records may include published_at: the timezone-explicit actual time immediately before initiating the final-file write, >= generated_at for Equity, within the issue weekend and not before Saturday 07:00. This is a publication-write record, not a claim about Vercel availability. Legacy records without it remain valid. Add this field only after confirming final absence and revalidating the freshly fetched draft. Do not change other draft content during this final serialization. Final equality means exact equality to the validated draft plus this one publication field; on retries, reuse the existing field, never compare against a newly invented timestamp. Equity publicationDecision accepts a candidate final including published_at. The draft itself need not carry published_at.

Final publication is an atomic main-head compare-and-swap. Fetch refs/heads/main and its commit/tree; fetch draft and final at that exact immutable commit. Verify final absence and validate that exact draft. Build a tree from that base tree adding only the missing final with candidate JSON (create_tree), then create_commit with exactly that head as parent, then update_ref(branch_name=main, sha=candidateCommit, expected_sha=validatedHead, force=false). The final file must be absent in the validated base tree. Never use an unleased create_file fallback for finals, overwrite a final, change the issue date, or force a ref. If these tools are unavailable, report the blocker and let the next run retry. Draft create_file/update_file remain permitted under the draft protocol.

If the main-head lease rejects, fetch current head, draft and final again. If the same final now exists, verify it and stop; conflicting final is a hard stop. Otherwise revalidate the current draft and build a new candidate on the new tree, preserving all intervening unrelated report writes. Retry head contention at most twice in one run, then defer to the next scheduled invocation. Unreferenced rejected trees/commits are not publications. After a successful or uncertain ref write fetch main and exact final and verify complete content equality with the intended candidate (including published_at); check an uncertain outcome before any retry. GitHub timestamp/commit and production deployment remain independent evidence.

For Macro retain the four content fields unchanged plus optional published_at. For Equity retain every required schema/source/asset check plus audit metadata above. Required sources that cannot be verified still block publication, even late. Never weaken a check to meet the clock or fabricate missing values. No email/Telegram or unrelated settings changes.

## Bounded retry and completion

Each run retries known transient read/network failures at most twice, respecting Retry-After. An access denial, missing authorization or invalid required data is not transient. Recheck unknown writes before retrying. Keep each run bounded; after a blocker report the issue date, stage, exact reason and last successful step, then let the next hourly publisher retry. Saturday 07:00/08:00 and recovery jobs do not wait indefinitely for another worker. A Sunday 23:00 run that remains blocked reports unresolved end-of-weekend recovery; no automatic Monday publication. Never disable tasks because one issue failed, and never promise the platform cannot pause them.

A Git commit is not live publication. Verify the exact content commit (or a later production commit containing identical final bytes) in the existing Vercel project, production READY, then the exact dated page and shared listing. A later deployment is acceptable only after fetching the final at that deployed SHA and proving identical content. Report Git-saved/deployment-pending/live separately. Never redeploy, change settings, or bypass access restrictions. On verified new live publication send one concise link and true delay information; identical already-live issues produce no repeated success message. Changes in blocker or an unresolved terminal failure deserve an update, not identical hourly alerts.
